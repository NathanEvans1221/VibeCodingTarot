## ADR-001: 使用 JSON 檔案儲存塔羅牌資料

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要選擇一種方式儲存 22 張（未來 78 張）塔羅牌的資料，包括牌名、含義、描述等。

### 決策

使用 JSON 檔案 (`data/tarot_cards.json`) 儲存塔羅牌資料，而非使用資料庫。

### 理由

1. **資料性質**: 塔羅牌資料為靜態資料，不需要複雜的查詢或關聯
2. **簡化部署**: 無需安裝或設定資料庫服務
3. **版本控制**: JSON 檔案可直接納入 Git 版本控制
4. **易於維護**: 開發者可直接編輯 JSON 檔案

### 結果

- ✅ 部署簡單，僅需 Python + Flask
- ✅ 資料易於閱讀和編輯
- ⚠️ 不適合大量資料或複雜查詢
- ⚠️ 並發讀取效能有限

## ADR-002: 前端渲染占卜結果

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要決定占卜結果的渲染方式：前端渲染 vs 後端渲染。

### 決策

使用 JavaScript 在前端處理占卜邏輯和結果渲染。

### 理由

1. **用户体验**: 即時回應，無需重新載入頁面
2. **伺服器負擔**: 減少伺服器運算量
3. **互動性**: 支援更豐富的動畫效果

### 結果

- ✅ 快速的用戶體驗
- ✅ 減輕伺服器負擔
- ⚠️ 無法進行伺服器端驗證
- ⚠️ 資料安全性需依賴前端過濾

## ADR-003: 使用 Flask 框架

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要選擇 Python Web 框架來實作後端 API。

### 決策

使用 Flask 作為後端 Web 框架。

### 理由

1. **輕量級**: 適合小型專案，學習曲線低
2. **靈活性**: 不強制特定的專案結構
3. **社群**: 擁有豐富的擴充套件和社群支援
4. **文檔**: 完善的官方文檔和教程

### 結果

- ✅ 快速開發和原型製作
- ✅ 易於理解和維護
- ⚠️ 大型專案可能需要更多結構

## ADR-004: 單頁模板模式

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要決定 HTML 模板的組織方式。

### 決策

每種占卜類型使用獨立的 HTML 模板，而非使用模板繼承。

### 理由

1. **簡單性**: 每個頁面獨立，易於理解
2. **維護性**: 修改單一頁面不影響其他頁面
3. **初學者友好**: 降低學習 Flask 模板的門檻

### 結果

- ✅ 頁面獨立，易於維護
- ⚠️ 存在程式碼重複（header/footer/JS）
- ⚠️ 不利於一致性的維護

### 後續改進

應考慮使用 Jinja2 模板繼承來減少重複：
```
templates/
├── base.html        # 基礎模板
├── index.html       # 繼承 base.html
├── single_card.html # 繼承 base.html
└── three_cards.html # 繼承 base.html
```

## ADR-005: 無使用者帳號系統

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要決定是否實作使用者帳號系統。

### 決策

初期不實作使用者帳號系統，占卜記錄僅保存在前端（LocalStorage）。

### 理由

1. **降低複雜度**: 無需處理認證、授權、資料庫
2. **快速上線**: 專注於核心占卜功能
3. **隱私保護**: 不收集使用者個人資料

### 結果

- ✅ 快速開發和部署
- ✅ 無需處理帳號相關安全問題
- ⚠️ 使用者無法跨裝置同步占卜記錄
- ⚠️ 無法提供歷史記錄查詢功能

### 後續改進

v0.2 可考慮新增簡單的本地記錄功能（無需帳號）。

## ADR-006: 紫色漸層主題

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要決定網站的視覺主題。

### 決策

使用紫色漸層 (`linear-gradient(#667eea → #764ba2)`) 作為主要視覺主題。

### 理由

1. **主題契合**: 紫色與神秘學、塔羅牌的意象相符
2. **視覺吸引力**: 漸層效果現代且美觀
3. **一致性**: 統一的視覺語言

### 結果

- ✅ 品牌識別度高
- ✅ 營造神秘氛圍
- ⚠️ 需確保文字可讀性

## ADR-007: RESTful API 設計

**日期**: 2026-08-02  
**狀態**: 已採用  
**決策者**: 開發團隊

### 背景

需要決定 API 的設計風格。

### 決策

使用 RESTful 風格設計 API，統一 JSON 回應格式。

### 理由

1. **業界標準**: REST 是最廣泛使用的 API 設計風格
2. **可預測性**: 開發者容易理解和使用
3. **可擴展性**: 易於新增新端點

### 回應格式

```json
{
  "success": true|false,
  "data": {...},
  "message": "描述訊息"
}
```

### 結果

- ✅ API 一致且易於使用
- ✅ 易於文件化和測試
- ✅ 支援前端和第三方整合
